# Releasing Bridgey

Bridgey publishes a signed Android APK and a macOS DMG and ZIP from tags
matching `v*`, with SHA-256 checksums, SBOMs, and build provenance.
Without Apple secrets the Mac build uses an ad-hoc signature; when those
secrets are configured, the same workflow adds Developer ID signing and
notarization.

## Android signing

Create one long-lived release keystore and keep two offline backups. The same
key must sign every direct-download APK update.

Add these repository secrets under **Settings → Secrets and variables →
Actions**:

- `ANDROID_KEYSTORE_BASE64`: base64 text of the `.jks` file
- `ANDROID_STORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

Google Play is optional for GitHub releases. If Bridgey is later published on
Google Play, enroll in Play App Signing and keep a separate upload key.

## macOS signing and notarization

Enroll in the Apple Developer Program and create a **Developer ID Application**
certificate. Export the certificate and private key from Keychain Access as a
password-protected `.p12` file.

Create an App Store Connect API key with access suitable for notarization, then
add these repository secrets:

- `MACOS_CERTIFICATE_BASE64`: base64 text of the `.p12`
- `MACOS_CERTIFICATE_PASSWORD`
- `MACOS_SIGNING_IDENTITY`: full `Developer ID Application: … (TEAMID)` name
- `APPLE_API_KEY_BASE64`: base64 text of the `AuthKey_….p8` file
- `APPLE_API_KEY_ID`
- `APPLE_API_ISSUER_ID`

The workflow imports the certificate into a temporary keychain, signs Bridgey
with Hardened Runtime and a secure timestamp, submits the DMG through
`notarytool`, staples the accepted ticket, and verifies it with Gatekeeper.

## Publish

1. Update Android `versionName`/`versionCode` and macOS bundle versions.
2. Commit and push `main`; wait for the Build workflow to pass.
3. Create and push an annotated tag such as `v0.1.0`.
4. The Release workflow creates the GitHub Release and attaches installers,
   checksums, and SBOMs, and records build provenance attestations.

## Release assets

Each release publishes:

- `Bridgey-Android.apk`: the signed Android app
- `Bridgey-macOS.dmg` and `Bridgey-macOS.zip`: the macOS app
- `SHA256SUMS-Android.txt` and `SHA256SUMS-macOS.txt`: SHA-256 checksums of
  the files above and of the SBOMs
- `Bridgey-Android.cdx.json` and `Bridgey-macOS.cdx.json`: CycloneDX 1.6
  software bills of materials (SBOMs)

The Android SBOM is generated by the CycloneDX Gradle plugin
(`./gradlew :app:cyclonedxDirectBom`) from the app's `releaseRuntimeClasspath`,
so it lists the libraries Gradle resolved for the release build, including
`:core:discovery` and its dependencies. It is the dependency set at build time:
R8 may remove unused code from the APK, and the SBOM does not list the Android
platform or build tools. The macOS SBOM is written by the Release workflow. The
Swift package has no package dependencies, so it names only the app, its
version from `Info.plist`, and the Swift, Xcode, and macOS versions used to
build it. Apple system frameworks are not listed.

The Release workflow also creates GitHub artifact attestations: signed SLSA
build provenance for every release asset, and SBOM attestations that link each
SBOM to the APK, DMG, and ZIP it describes. Attestations are stored by GitHub
and are not attached to the release as files.

## Verifying a download

Check the SHA-256 checksums from the folder that contains the downloaded files:

```sh
shasum -a 256 -c SHA256SUMS-Android.txt
shasum -a 256 -c SHA256SUMS-macOS.txt
```

Use `--ignore-missing` to skip files you did not download. A matching checksum
shows the file is the one listed next to it; it is only as trustworthy as the
place the checksum file came from.

With the [GitHub CLI](https://cli.github.com), verify that a file was built by
this repository's Release workflow:

```sh
gh attestation verify Bridgey-macOS.dmg --repo singeol/bridgey
```

To check the SBOM attestation instead of the provenance attestation:

```sh
gh attestation verify Bridgey-macOS.dmg --repo singeol/bridgey \
  --predicate-type https://cyclonedx.org/bom
```

For a stricter check, add
`--signer-workflow singeol/bridgey/.github/workflows/release.yml` and
`--source-ref refs/tags/v0.1.0` with the tag of the release.

Attestations prove that the file was built by the Release workflow on a
GitHub-hosted runner from the tagged commit. They do not review the source,
and they do not replace Android signing or Apple Developer ID signing and
notarization: Android and macOS still check those signatures when installing
or opening Bridgey. Releases published before attestations were added have
none.

Release notes should retain the acknowledgement: “Built with the assistance of
OpenAI Codex.”
